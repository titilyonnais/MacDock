# Restyler les apps XAML de Windows 11 façon macOS (recherche du 8 octobre 2026)

## 0. Ce qui est XAML et ce qui ne l'est pas (vérifié sur ce PC, build 26300)

| Cible | Processus | Technologie |
|---|---|---|
| Explorateur : onglets, adresse, recherche, barre de commandes, Accueil, Galerie, volet Détails | explorer.exe | **WinUI 3** (Windows App SDK du système : `Microsoft.WindowsAppRuntime.CBS*`, `FileExplorerExtensions.dll`), îlot `Microsoft.UI.Content.DesktopChildSiteBridge` |
| Menu contextuel moderne | explorer.exe | **WinUI 3**, fenêtre `XamlExplorerHostIslandWindow_WASDK` |
| Volet de navigation | explorer.exe | Win32 : `NamespaceTreeControl > SysTreeView32`, dans un `DirectUIHWND` |
| Liste de fichiers | explorer.exe | **DirectUI** (dui70.dll) : `SHELLDLL_DefView > DirectUIHWND`, avec des ScrollBar Win32 |
| Barre d'état | explorer.exe | **DirectUI**, dessinée dans le `DirectUIHWND` du cadre |
| Paramètres | SystemSettings.exe | UWP `Windows.UI.Xaml` |
| Calculatrice, Horloge | CalculatorApp.exe, Time.exe | UWP + WinUI 2.8 |
| Bloc-notes, Photos | Notepad.exe, Photos.exe | **WinUI 3** (Windows App Runtime 2) ; la zone de texte du Bloc-notes est un RichEdit `RichEditD2DPT` |

## 1. Le moteur des stylers de m417z

Les sources sont dans `ramensoftware/windhawk-mods/mods/` : `windows-11-taskbar-styler`, `-start-menu-styler`,
`-notification-center-styler`, `-file-explorer-styler`, `-settings-styler`. Le moteur, issu d'ExplorerTAP
(TranslucentTB), s'appuie sur l'API officielle de diagnostic XAML (`InitializeXamlDiagnosticsEx`).

### Déroulé de l'injection
1. **Attendre la fenêtre hôte XAML.** Crochets sur `CreateWindowExW` et `CreateWindowInBand(Ex)` :
   - barre des tâches : `DesktopWindowContentBridge` ;
   - Paramètres : `Windows.UI.Core.CoreWindow` ;
   - Explorateur : `CabinetWClass` ou `XamlExplorerHostIslandWindow_WASDK`.

   Pour les fenêtres déjà ouvertes, `Wh_ModAfterInit` les parcourt et lance l'injection sur leur fil
   (`RunFromWindowThread`).
2. **Injecter le TAP** avec `InitializeXamlDiagnosticsEx` :
   - en UWP, depuis `Windows.UI.Xaml.dll`, connexion `VisualDiagConnection1…10000` ;
   - en WinUI 3, depuis `Microsoft.Internal.FrameworkUdk.dll`, connexion `WinUIVisualDiagConnection1…10000`.

   Le TAP est la DLL du mod elle-même.
3. **Recevoir le site.** `DllGetClassObject` crée le `WindhawkTAP` (`IObjectWithSite`). Son `SetSite` reçoit
   `IXamlDiagnostics` et crée un `VisualTreeWatcher`.
4. **Suivre l'arbre visuel.** `IVisualTreeService3::AdviseVisualTreeChange` est appelé depuis un fil créé exprès :
   depuis le fil d'interface, l'app se bloque.
5. **Appliquer les règles à chaque ajout d'élément.**
   - Les règles s'écrivent `Classe#Nom[Prop=Val] > …`.
   - Chaque valeur est construite par un `<Style><Setter/></Style>` passé à `XamlReader::Load`, puis posée avec
     `SetValue`.
   - L'original est gardé (`ReadLocalValue`) et réappliqué si l'app change la valeur (`RegisterPropertyChangedCallback`).
   - Des valeurs peuvent dépendre de l'état visuel (`VisualStateGroup`).
6. **Fusionner les ressources** dans `Application::Current().Resources()`, avec `ThemeDictionaries` Dark et Light.
   Cette fusion doit attendre le premier élément ajouté.

UWP et WinUI 3 utilisent le même code, compilé contre `Windows::UI::Xaml` ou `Microsoft::UI::Xaml`. Un même mod peut
ouvrir les deux connexions (exemple : CJK Spacer).

### Pièges
- **Un seul consommateur de diagnostic par framework et par processus.** Conflits connus avec ExplorerBlurMica et
  TranslucentTB.
- **Corruption du tas** dans les processus à plusieurs fils d'interface. Parade : faire croire que
  `HKLM\Software\Microsoft\XAML\Debug\DisableCompositionDiag` vaut 1, par un crochet sur le registre.
- **Fuite mémoire** sans `IXamlDiagnosticsTestHooks::UnregisterInstance`.
- **Arrêt de l'app** si une règle provoque un cycle de mise en page.
- **Plantage au déchargement** si un pinceau survit à la DLL.
- **`OnVisualTreeChange` doit toujours renvoyer `S_OK`**, sinon les notifications cessent.
- **Statistiques :** les stylers envoient des statistiques d'usage (à retirer dans un fork).
- **Licence :** GPL v3.

## 2. Styler générique ou un mod par app ?
Aucun styler générique n'existe, mais le moteur est générique :
- le Settings Styler se déclenche sur n'importe quelle `CoreWindow` ; un fork avec `@include CalculatorApp.exe` et
  `Time.exe` devrait fonctionner (à tester) ;
- pour le Bloc-notes et Photos, il faut le moteur WinUI 3, sans les crochets propres à l'Explorateur ; le déclenchement
  se ferait sur `WinUIDesktopWin32WindowClass` (à confirmer).

**Surcharges globales.** Les « resource variables » (`Clé=Valeur` ou `Clé:=<XAML>`) permettent de changer en une fois
`ControlCornerRadius`, `OverlayCornerRadius`, les `SystemAccentColor*` et les pinceaux `Button*`, `ToggleSwitch*`,
`Slider*`, `ScrollBar*`. Mais :
- seuls les éléments qui résolvent la ressource après la fusion sont touchés ;
- les ressources locales et les valeurs codées en dur dans les gabarits passent devant.

Il faut donc combiner ressources et règles ciblées. Pour inspecter les éléments : UWPSpy.

## 3. Liste de fichiers et volet de navigation (DirectUI et Win32)
Le diagnostic XAML ne fonctionne pas ici. Techniques connues :
- **Crochets GDI et uxtheme** (repris de Translucent Windows) : `FillRect`, `PatBlt`, `ExtTextOutW`,
  `DrawThemeBackground(Ex)` et `Polyline`. ExplorerBlurMica suit la même idée.
- **Sélection et survol :** `DirectUI::Element::PaintBackground` dans dui70 (mod Explorer Visual Tweaks Dark).
- **Réécriture de la mise en page :** `DirectUI::DUIXmlParser::SetXML`, qui réécrit le balisage UIFILE. C'est puissant
  mais fragile.
- **Arbre de navigation :** `SysTreeView32` passe par `DrawThemeBackground` (mod Explorer TreeItem Tweaker).

**Limites :** pas de styles déclaratifs, une sélection en pilule à peindre soi-même, et des crochets par symboles qui
cassent à chaque build.

## 4. Risques
- **Noms d'éléments versionnés** (`CommandBarControl_Wave1`) : une règle cesse de s'appliquer, sans plantage.
- **Crochets par symboles :** ils dépendent de la build de Windows.
- **Plantage d'explorer.exe :** il emporte la barre des tâches avec lui.
- **Coût :** un rappel par élément ajouté.

## 5. Architecture recommandée
1. **A. Thèmes MacDock pour les stylers existants** (Explorateur et menu contextuel, Paramètres) : de simples réglages
   (`controlStyles`, `themeResourceVariables`, `styleConstants`), écrits par notre installateur dans
   `HKLM\SOFTWARE\Windhawk\Engine\Mods\<id>\Settings`. Tout le dessin est fait en XAML, donc aucune ressource Apple.
2. **B. Mod `macdock-xaml-uwp`** : fork du Settings Styler pour la Calculatrice et l'Horloge, avec des ressources
   globales (rayons, accent, interrupteurs, curseurs, barres de défilement) et sans statistiques. Licence GPL v3.
3. **C. Mod `macdock-xaml-winui3`** : moteur WinUI 3 pour le Bloc-notes et Photos.
4. **D. Mod `macdock-explorer-dui`** : transparence et barres de défilement par GDI et uxtheme, sélection par
   `PaintBackground`. À ne pas cumuler avec l'effet translucide du File Explorer Styler.
5. **Règles transverses :**
   - aucun de nos mods XAML dans explorer.exe tant qu'on utilise les stylers de m417z (un seul consommateur de
     diagnostic) ;
   - `macdock-look` (polices) reste à part ;
   - repasser UWPSpy après chaque mise à jour de Windows.
